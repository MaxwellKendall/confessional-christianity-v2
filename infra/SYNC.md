# Account sync

Use the stage stack's `AccountSyncUrl` with a Cognito user-pool JWT from the stage's studio pool (`Studio-dev` / `Studio-prod`) and `confessional` app client (dev also accepts the legacy `ConfessionalChristianity-dev` pool until TKL-965). AppSync verifies the token and `appIdClientRegex`. The resolver uses its `sub` for every ownership check and derives the stream from that subject. The client cannot supply a stream, owner or guardian.

## Rows

| --- | --- | --- |
| `children` | Local child UUID, also used as `child_id` | `name`, `age`, `created_at`, `active_catechism_id` |
| `catechism_assignments` | Persisted UUID per child's catechism assignment | `catechism_slug`, `started_at`, `started_at_question` |
| `catechism_pacing` | Persisted UUID per child's catechism pacing row | `catechism_slug`, `current_question` |
| `catechism_milestones` | Persisted UUID per child's catechism question milestone | `catechism_slug`, `question`, `state`, `introduced_at`, `review_count` |
| `lords_day_notes` | Local note UUID, also used as `note_id` | `service_date`, `passage_ref`, `sermon_title`, `preacher`, `church`, `extracted_text`, `created_at` |
| `note_cards` | Local card UUID (parent in `note_id`) | `kind`, `body`, `verse_ref`, `attribution`, `palette`, `position`, `edited_by_user`, `created_at` |

Each table tracks its own `SyncRowMeta.updatedAt` per row so last-write-wins resolves independently for assignment, pacing and each individual milestone (e.g. a pacing change does not block a newer milestone edit). Rows pulled from a co-guardian keep their server `row_id` in `SyncRowMeta` so subsequent edits and tombstones reuse the exact same ID. Deleting a child locally enqueues separate tombstones for each milestone, pacing, and assignment row as well as the `children` row.

Clients can create UUIDs offline. Reuse the same row ID for future updates, and treat UUID casing as insignificant. The server returns lowercase UUIDs. Each child-table ID is unique per table and bound to one child (`child_id`, with `note_id` null). Each Lord's Day note or card ID is unique per table, private to the verified Cognito subject (never shared with co-guardians), and bound to one parent note (`note_id`, with `child_id` null). Card writes require an existing parent note owned by the caller. The payload is a complete row snapshot, encoded as a JSON object string (up to 4 KiB; up to 64 KiB for `lords_day_notes` to accommodate multi-page `extracted_text`). Its fields take scalar JSON values: names, slugs, timestamps, note text, card kinds and milestone states are strings; ages, question numbers, positions and review counts are numbers; `edited_by_user` is a boolean. For `note_cards`, `kind` must be strictly `key_point`, `quote` or `verse`, `position` must be a non-negative integer, and `verse` cards require a non-empty `verse_ref` with empty/null `body`. Photos are never accepted or stored in sync storage. Omit unset fields or use null.

Creating a child makes the verified caller its owner. A co-guardian may read and edit its records, including the profile. Only the owner may tombstone the profile. Tombstones are row-level. A transport removing a child should enqueue separate tombstones for its progress rows and remove its local child and progress from the UI. Creating a Lord's Day note makes the verified caller its sole owner (`note#<id>` / `access`), and only that owner may read, update, attach cards to, or tombstone the note or its cards.

Membership is stored on the child access item as a map of stable membership UUIDs to verified Cognito subjects. Membership is managed by trusted backend code. The public API provides no membership writes or invitation endpoint. Trusted provisioning must verify the owner and grantee, cap the child at eight co-guardians, and update the access item's version whenever membership changes. For existing rows to appear in a new guardian's stream, grant provisioning must append references with fresh cursor values under the same counter compare-and-swap described below, rechecking the row revision and access version for each backfill. Stream reads recheck current membership before serving data.

## Push and pull

`pushSync(changes: [SyncChangeInput!]!): [SyncPushResult!]!` accepts up to 20 changes per request, in outbox order. Each change carries the outbox UUID `id`, `table`, stable `row_id`, either `child_id` (child/catechism tables) or `note_id` (Lord's Day tables), `updated_at`, optional `deleted_at` and `payload`. Use UTC ISO 8601 instants with at most millisecond precision. Omit payload for a tombstone.

The response returns one `SyncPushResult` (`id`, `status`, `reason`) per input change, in the same order:

- `ACCEPTED` (`reason: null`): the write committed, or the caller is authorized and the stored row's `updated_at` is already equal to or newer than the pushed `updated_at` (an equal timestamp keeps the first accepted write). Remove the entry from the outbox.
- `REJECTED` (permanent; do not retry): the server rejected this change and continued processing later changes in the batch. Remove the entry from the outbox so a stale or invalid change cannot block later writes. `reason` is one of:
  - `UNAUTHORIZED`: the caller is not the owner or a current guardian for `child_id` (or not the owner of `note_id`), the parent child or note does not exist or is retired, a co-guardian tried to tombstone a `children` profile, or `row_id` belongs to a different parent child/note.
  - `INVALID_INPUT`: unknown table, invalid row/child/note UUID, child `row_id` ≠ `child_id`, note `row_id` ≠ `note_id`, cross-scope `child_id`/`note_id`, invalid timestamp syntax, invalid card `kind`/`position`/verse fields, disallowed or oversized payload, or a tombstone with a payload.
  - `CLOCK_SKEW`: `updated_at` (or `deleted_at`) is more than 24 hours past server time. Rejecting future-dated writes prevents a skewed device clock from locking a row out of last-write-wins updates.
- `RETRY` (`reason: CONTENTION`): write contention exhausted the server's optimistic-concurrency retries. To preserve outbox ordering (for example, child creation before its progress rows, or note creation before its cards), the server stops applying further changes in the batch and returns `RETRY` (`CONTENTION`) for the contended change and every remaining entry after it. Keep `RETRY` entries in the outbox and resend them with their original timestamps and IDs after backoff.

Request-level failures (unauthenticated caller, account marked `disabled` for deletion, more than 20 changes, a non-UUID outbox `id`, or an unexpected backend error) still throw a top-level GraphQL error. Each accepted change commits independently, and already accepted changes replay as `ACCEPTED` no-ops.

`pullSync(table: String!, after: String = "0", limit: Int = 50): [SyncRecord!]!` returns up to 100 rows per page. Each row includes `table`, `id` (the stored row UUID), `child_id` (child/catechism tables), `note_id` (Lord's Day tables), `updated_at`, `deleted_at`, `payload` and `change_id`. Decode the decimal cursor string as a Swift `Int64` and store it per signed-in subject and table. Start with `"0"`, and request subsequent pages strictly after the last applied `change_id` until fewer than the requested count are returned. Apply a non-null `deleted_at` as a local delete.

A DynamoDB transaction replaces the canonical row, compares the parent child or note access version, and advances and publishes each authorized recipient's stream together. Counters live on the account partition and monotonically increase across tables, so gaps in a table are expected. Pull uses strongly consistent reads and returns only the current row revision. Superseded references and rows the caller can no longer access are filtered before returning a page.

## Account deletion contract (TKL-890)

The deletion worker must use the same stage table and the verified Cognito subject. It must be able to resume the following steps after a partial failure.

1. After any required Apple revocation succeeds, set an `account#<sub>` / `disabled` item before enumerating data. Keep a version on the marker. Push checks for absence in every transaction. Keep the marker after removing the Cognito user, so an unexpired JWT cannot recreate or read sync data.
2. Query `owned#` entries under `account#<sub>`. Verify the `owner` on each `child#<id>` / `access` item. Use a conditional write to retire access with a new `version` and `retired: true`. Keep the original owner and membership map on the retired item until cleanup finishes so a retry can confirm ownership and remove the co-guardians’ reverse membership entries. Enumerate the child's `row#<table>#<id>` catalog entries and delete their `record#<table>#<id>` / `value` items and the catalog entries. Remove each ownership index entry only after the child cleanup succeeds. Retiring access first invalidates in-flight writers. After cleanup, retain only the version and retired flag to reserve the child UUID without keeping an owner or guardian list. Other guardians' old stream references no longer resolve to data.
3. Query `owned_note#` entries under `account#<sub>` (private Lord's Day notes and their cards). Verify the `owner` on each `note#<id>` / `access` item and conditionally retire it with a new `version` and `retired: true`, keeping `owner` until cleanup finishes so a retry can resume safely. Enumerate the note's `row#<table>#<id>` catalog entries (covering both `lords_day_notes` and `note_cards` rows bound to that note) and delete each `record#<table>#<id>` / `value` item and its catalog entry. Remove each `owned_note#<id>` index entry only after cleanup succeeds, then retain only `version` and `retired: true` on `note#<id>` / `access` to reserve the note UUID without keeping `owner`.
4. Remove this subject from the access maps of children owned by other accounts using a conditional update on the access version. Trusted membership provisioning should maintain a reverse `member#<child-id>` entry under the guardian's account in the same transaction as the grant, and condition the grant on the guardian's disabled marker being absent. Remove both membership entries together. Preserve the other owner's child, progress and other co-guardians.
5. Purge the departing subject's published references under `change#` (covering child, catechism, `lords_day_notes` and `note_cards` streams) after all of their memberships, owned children and owned notes have been removed, then remove their sequence. References in other accounts contain only row locators, revision identifiers and cursors. The deletion worker may remove references to purged child rows without renumbering or resetting any remaining guardian's sequence. Delete the Cognito user after cleanup.
